## Purpose

This is a fresh report, not an edit of the prior options files. It records the
current state of `maestro-orchestrate` after the reduction pass on branch
`refactor/codebase_reduction`, checks off what is already implemented, and lays
out additional architecture-driven reduction options. The risk posture is
intentionally broad: public contract breaks, package splits, dependency
replacement, state rewrites, generated-surface deletion, and product-scope
cuts are all included as options.

- **Observed**: checked in this checkout during this report pass.
- **Inferred**: likely payoff based on observed code and package shape.
- **Assumed**: acceptable only because the requested posture allowed risky and
  breaking options.

## Option Details

### A. MCP Action Registry

Current state: command tables exist, but the public surface is still 40 named
tools. The next design is a generated action catalog where each pack exposes
one action tool with `{ action, payload }`, and payload schemas are generated
from current Zod schemas.

Architectural payoff:

- Public MCP surface drops from 40 named tools to 5 pack-level tools, or even
  one `maestro` action tool if the product accepts a more generic interface.
- Tool docs, parity tests, and handler registration become generated from one
  table.
- Model selection may become worse because names are less specific; this must
  be dogfooded, not assumed.

Execution gates:

- Generate parity fixtures for all current tools.
- Run a full orchestration using only action tools.
- Compare model tool-selection quality against current named-tool traces.
- If breaking deletion is approved, delete old registrations and generated docs.

### B. Event-Sourced State Core

Current state: session, document, design-gate, memory, checkpoints, ratings,
archive, and knowledge state is split across Markdown, JSON, and JSONL files.
Repository modules exist, but the storage model is still file-family based.

Architecture:

- Define an append-only event stream for session and memory operations.
- Materialize current-session views from events.
- Keep export back to the current file layout for audit and rollback.
- Migrate only after a dry-run diff against real ignored `docs/maestro` state.

Why event log before SQLite:

- No native dependency.
- Easier rollback.
- Directly matches Maestro's phase/history domain.
- Gives retention and compaction a single source of truth.

### C. Local Artifact Retention

Current state: ignored local artifacts are large and volatile. Existing
`compact_archive` only prunes old Maestro session archives. The new
`src/tooling/local-artifact-retention.ts` command covers `.superpowers`,
`docs/superpowers`, `src/generated`, and generated `dist/src` declaration/map
byproducts in addition to Maestro archives.

Architecture:

- `npm run retention:local` builds the runtime and inventories artifacts in
  dry-run mode by default.
- Artifacts are classified as protected, durable, retained, or prunable.
- Deletion requires both `--apply` and `--confirm-prune-local-artifacts`.
- Active sessions and durable knowledge are preserved by default.
- The validated dry run found 408 prunable files and 4,628,617 prunable bytes,
  with zero files deleted.

This is the lowest-risk immediate cleanup, but it is local-state reduction, not
tracked-source reduction.

### D/E. MCP SDK Adapter And Replacement

Current state: runtime source imports `@modelcontextprotocol/sdk` server,
stdio transport, and roots notification primitives only through
`src/mcp/server/mcp-sdk-adapter.ts`. Package tarball size does not bundle the
dependency, but installation footprint and protocol ownership still depend on
the SDK.

Architecture:

- Create a first-party adapter with only the operations Maestro uses.
- Move direct SDK imports behind the adapter.
- Add wire-level stdio fixture tests for initialize, listTools, callTool, error
  normalization, and elicitation.
- Only then decide whether to replace the SDK.

Implemented evidence:

- `src/mcp/server/mcp-sdk-adapter.ts` exports server creation, stdio transport
  creation, server connection, and the roots-list-changed schema.
- `src/mcp/server/create-mcp-server.ts` and `src/mcp/maestro-server.ts` consume
  the adapter instead of direct SDK imports.
- Source import scan found MCP SDK imports only in the adapter.
- Adapter, create-server, runtime startup, pack composition, and Zod schema
  tests passed.

Replacement is high risk because MCP protocol drift would affect every runtime.

### F/G. Runtime Package Split And Payload Partitioning

Current state: one package carries all four runtime families. Package buckets
show `dist` dominates, then Claude, Qwen, root agents, Codex plugin files, and
runtime docs/context files.

Lower-risk precursor:

- Generate per-runtime payloads from `src/platforms/runtime-declarations.ts`.
- Package only the runtime content each runtime needs.
- Keep one package until parity and docs are generated.

Breaking split:

- `@josstei/maestro-core`
- `@josstei/maestro-gemini`
- `@josstei/maestro-claude`
- `@josstei/maestro-codex`
- `@josstei/maestro-qwen`

This can reduce per-consumer package weight but increases release complexity.

### H. Runtime Family Deletion

This is the far-left-field option. If the product does not need all four
runtimes, delete one or more runtime families instead of abstracting them.

Examples:

- Codex-only package and source tree.
- MCP-core-only package with no generated Gemini/Qwen/Claude checkout surfaces.
- Claude/Codex-only package with Gemini/Qwen retired.

This is the largest package and cognitive-load win, but it is a product
decision, not an engineering cleanup.

### I. Bundled Runtime Artifact

Current state: package carries many compiled `dist/src` modules as separate
files. A bundler could collapse public bins and MCP server runtime into fewer
files.

Risk:

- ESM dynamic imports, runtime asset paths, content registry loading, and
  package-root assumptions can break.
- Debugging and source maps become worse unless deliberately preserved.

Use a prototype branch only, with package startup tests across all runtimes.

### J. Descriptor-Generated Runtime Docs

Current state: runtime descriptors own metadata and package invariants, but
runtime docs are still authored files. Generate runtime docs from descriptors
and small prose fragments, then delete duplicated runtime inventory prose.

This should precede any package split because package split multiplies docs
unless generation owns them.

### K. Schema-Generated Test Matrix

Current state: tests are larger than source. The existing contract helper is a
good start, but many package, runtime, and MCP tests still encode one-off
fixtures.

Architecture:

- Generate one parity test per command-table entry.
- Generate one package invariant test per runtime declaration.
- Generate negative tests from schemas instead of hand-writing every shape.
- Keep hand-written behavioral tests for complex flows.

The goal is fewer test lines with stronger coverage of generated contracts.

### L. Handler Dependency Injection

Current state: several handlers accept loose `any` params and direct project
root strings. A handler-context layer exists, but the migration is incomplete.

Architecture:

- Define `SessionStore`, `MemoryStore`, `ContentProvider`, `Clock`,
  `FileSystem`, and `WorkspaceResolver` interfaces.
- Use a composition root for the MCP server.
- Keep handlers pure where possible and inject side effects.

This reduces future rewrite cost for event-log state, SDK adapter isolation, and
runtime package split.

### M. Decorator Or Metadata-Driven Tool Definitions

Decorators can reduce repeated command-table boilerplate, but they can also hide
important behavior. The safer version is metadata-first without runtime magic:

- command descriptor object
- schema reference
- handler reference
- workspace requirement
- generated docs/tests/registration

Use actual decorators only if TypeScript decorator metadata is already accepted
as part of the runtime style.

### N. Workflow Engine

Current state: orchestration lifecycle rules live in handlers, services, tests,
and prose protocols. A state-machine library or small internal reducer could
make legal transitions explicit.

Do this only if it deletes branching and test duplication. If the engine adds a
new abstraction while keeping old service branches, it is not a reduction.

### O. External Content Pack

Move agent bodies, shared skills, references, and templates into an optional
content package fetched by runtime packages, leaving core focused on MCP
protocol, state, and tooling.

This is attractive if package size and release cadence should separate content
from code. It is risky because offline install behavior and version skew become
first-order product concerns.

### P. Package-Only Generated Surfaces

Current state: root generated surfaces are ignored, but `npm run generate`
materializes them in a source checkout. A stricter model would generate them
only in `dist/package-staging` or release temp directories.

Payoff:

- Source checkout becomes smaller and quieter.
- Accidental edits to generated files become impossible.

Risk:

- Local runtime smoke tests, marketplace previews, and plugin development need
  staging-aware paths.

### Q. CLI Tooling Framework

Current state: `src/tooling/lib/cli.ts` exists, but scripts still contain
one-off argument handling and command wiring.

This is a tidy-up track, not the main reduction lever. Do it as files are
touched for package split, retention, or release checks.

### R. SQLite Backend

SQLite is still an option, but it should come after event-log parity. It adds a
native-ish operational dependency and migration problem. It is justified only if
query performance, concurrent writes, or cross-session analytics need it.

## Recommended Execution Plans

### Plan 1: Maintainability-First, Low Public Breakage

1. Finish handler dependency injection around session and memory stores.
2. Add event-log prototype in tests with import/export parity.
3. Generate runtime docs from descriptors.
4. Add schema-generated MCP/package parity tests.

Validation gates:

- `npm run typecheck`
- `npm run check:source`
- `npm run check:release`
- targeted event-log import/export fixture tests
- local MCP content startup tests across packaged runtime roots

Why this plan: it pays down structural coupling before breaking public contracts.

### Plan 2: Aggressive Breaking Reduction

1. Build action-registry prototype while retaining the 40 current tools.
2. Dogfood one full orchestration using action tools only.
3. If approved, delete the 40 named tool registrations and generated docs.
4. Partition runtime content per runtime.
5. Generate per-runtime package manifests.
6. Split packages and delete the all-runtime package surface after migration.

Validation gates:

- generated parity test per deleted tool
- full orchestration smoke using action-only tools
- per-runtime `npm pack --dry-run --json`
- per-runtime install/startup smoke
- marketplace metadata validation

Why this plan: it attacks public API surface and package weight, but it is
contract-breaking and should not be mixed with unrelated storage migration.

### Plan 3: Product-Scope Reduction

1. Choose the runtimes that are actually strategic.
2. Delete unsupported runtime descriptors, docs, generated surfaces, package
   invariants, and tests.
3. Collapse runtime abstractions that existed only to support deleted runtimes.
4. Regenerate package and release gates around the reduced product.
5. Rewrite public docs to match the smaller supported matrix.

Validation gates:

- runtime-specific package/startup tests only for retained runtimes
- release artifact verification
- docs inventory check
- migration/deprecation note if this is externally published

Why this plan: deleting product scope beats abstracting product scope. It is the
highest size win and the highest product risk.

### Plan 4: Runtime Packaging Reduction Without Product Deletion

1. Generate runtime docs from descriptors.
2. Generate per-runtime payload inventories.
3. Create per-runtime package dry-run tasks and budgets.
4. Publish split package prototypes locally.
5. Keep the current all-runtime package until external install paths are proven.
6. Decide whether to deprecate the all-runtime package or keep it as a meta
   package.

Validation gates:

- per-runtime pack reports
- per-runtime startup tests
- package budget comparison against current 335-entry package
- migration guide review

Why this plan: it reduces what each consumer installs while retaining all four
runtime products.

## Decision Recommendation

Recommended next sequence if maintainability remains first priority:

1. **L: Handler dependency injection** - prepares state and runtime rewrites.
2. **B: Event-sourced state core** - largest architectural cleanup still open.
3. **J/K: Descriptor docs and generated parity tests** - required before
   public/package breaks.
4. **A or F/G** - choose action-registry public break or runtime package split
   after the foundations are proven.

Recommended next sequence if raw size is first priority:

1. **H: Delete runtime families** if product scope allows it.
2. **F/G: Split or partition runtime package output** if all runtimes remain.
3. **K: Generate test matrices** to reduce test volume after contract shape is
   stable.
4. **O: External content pack** if content and code should version separately.

Recommended next sequence if maximum risk is acceptable:

1. Delete all non-strategic runtime families.
2. Replace 40 MCP tools with one action-router tool.
3. Replace file-family state with an event log.
4. Bundle runtime code to a minimal package artifact.
5. Externalize content into a separately versioned content pack.
6. Remove compatibility docs, shims, and legacy package paths in the same major
   release.
