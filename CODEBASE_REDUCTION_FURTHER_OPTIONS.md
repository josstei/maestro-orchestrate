# Further Codebase Reduction Options

Date: 2026-07-09

## Purpose

This report is a fresh decision menu for further reducing `maestro-orchestrate`
after the TypeScript/dist terminal work, command-table migration, runtime
content registry, and agent-profile compaction already landed.

The scope is intentionally broad. Breaking public contracts, changing package
topology, adding dependencies, deleting committed generated output, replacing
state architecture, and splitting runtimes are all considered valid options if
the resulting system is simpler and behavior can be re-proven.

This started as a decision artifact plus an implementation-ready phase plan.
The execution status section below records which options have now been carried
through implementation and validation in this checkout.

## Evidence Model

This report uses the repository evidence tiers from `AGENTS.md`:

- **Observed** means a count, file path, command, or behavior was checked in
  this checkout.
- **Inferred** means a recommendation, expected reduction, or architectural
  payoff follows from observed evidence but still requires implementation and
  validation.
- **Assumed** means the report is carrying the user's explicit risk posture:
  breaking public contracts, changing package topology, and deleting generated
  output are allowed options, but each still needs a separate execution
  approval.

All reduction estimates below are inferred unless a line explicitly says it is
observed. Tracked-size reduction uses `git ls-files` counts. Filesystem counts
are used only for local generated byproducts or ignored state.

## Ranking Rubric

Options are ranked by:

1. Architectural leverage: removes repeated decisions or fragile ownership
   boundaries.
2. Size impact: reduces tracked files, tracked lines, package bytes, test lines,
   or ignored local mass.
3. Behavior safety: can be proven by current source/release gates plus targeted
   runtime probes.
4. Strategic optionality: creates a foundation for later, riskier reductions.

## Recommended Stack

The strongest low-to-medium-risk stack has now been executed:

1. [x] Artifact/package policy is centralized in one typed contract.
2. [x] Repository topology is source-first, with `dist/src` generated for local
   runtime, package, and release validation.
3. [x] Session lifecycle has repository/service boundaries.
4. [x] Runtime declarations drive metadata, docs, package invariants, and
   payload rows.
5. [x] Security-sensitive policy parsing is split before any parser dependency
   or DSL adoption.
6. [x] Package/runtime tests share contract fixtures.
7. [x] Runtime payload and npm docs/changelog/package docs are pruned.

The remaining decision menu is intentionally breaking:

1. Prototype a 40-tool-to-5-action MCP registry only after dogfooding model
   selection quality.
2. Prototype a structured event log before SQLite or any native state backend.
3. Delay runtime package externalization until descriptor-generated docs and
   per-runtime package gates exist.
4. Isolate the MCP SDK behind an adapter before attempting replacement.

## Option 1: Source-Only Repository, Generated Dist Release

**Execution status:** Completed
**Rank:** 1
**Risk:** Very high
**Primary win:** Tracked size and cognitive load
**Secondary win:** Cleaner source/release boundary
**Breaking surface:** Repository workflow, local runtime expectations, dist-branch publishing

Delete committed `dist/src` from the development branch and generate it only for
package/release artifacts or a dedicated `dist` branch.

Observed support:

- `dist/src` is now 0 tracked files and 0 tracked lines.
- Local `dist/src` has 383 generated files and 19,707 filesystem lines after
  `npm run build`, including 186 ignored declaration/source-map files totaling
  4,466 lines.
- `dist/src` is rebuilt by `npm run build`; package verification already builds
  before packing.
- Package/runtime behavior depends on generated `dist/src`, but development
  source review does not need both trees in the same branch if release tooling
  can prove the artifact.

Architectural payoff:

- The repository becomes source-first again while the package remains
  dist-terminal.
- Code review stops mixing human-authored source and compiled runtime output.
- Reduction accounting becomes honest: generated JS no longer doubles every
  TypeScript change.

Observed reduction:

- Removed 21,172 tracked `dist/src` lines and 186 tracked `dist/src` files from
  the development branch.
- No direct package reduction unless paired with package pruning.
- Local ignored declaration cleanup is a separate retention/build-output issue,
  not part of the tracked repository reduction.

Main risks:

- Existing package/plugin consumers may rely on repository checkout entrypoints
  without running `npm run build`.
- Tests currently import from `dist/src` intentionally. They would need an
  explicit build fixture or generated temp dist.
- A current read-only audit found 152 test files that mention `dist/src`,
  `tests/support/dist`, or `ensureBuiltDist`; Phase 2 must inventory those
  files before changing test topology.
- Release workflows must prove that the published artifact carries the exact
  generated output.

Validation gates:

- `npm run check:source`.
- `npm run check:release`.
- source-only clone smoke test: build, generate, MCP startup, and package dry run.
- dist-branch publish dry run.
- packed-package install tests.
- explicit decision gate before deleting tracked `dist/src` from the
  development branch.

Recommendation:

Completed in this execution pass. Keep source-only checkout smoke tests and
release/package gates as the safety net for this topology.

## Option 5: Runtime Content Payload Compression Or Partitioning

**Execution status:** Compression completed; partitioning not executed
**Rank:** 5
**Risk:** Medium to high
**Primary win:** Package unpacked size
**Secondary win:** Startup/content boundaries
**Breaking surface:** Runtime content loader internals

The runtime registry solved raw source packaging, but the packed payload is now
the largest package bucket. The next options are:

- split payload by resource type: agents, skills, references, templates,
  blueprints
- load only the requested segment
- compress the payload and decompress in memory
- generate per-runtime transformed payloads only if it reduces runtime work
  without duplicating too much content
- keep source-checkout filesystem fallback only for development

Observed support:

- `dist` is now 522,535 unpacked npm bytes after payload compression.
- `dist/src/generated/runtime-content-registry.txt.gz` replaced the raw payload
  and npm no longer ships `runtime-content-registry.txt`.
- `runtime-content.ts` already materializes registry entries through offsets.

Architectural payoff:

- Content loading becomes explicit and measurable.
- Package budgets can target content families separately.
- A future runtime split can ship only the content needed by that runtime.

Raw reduction potential:

- High unpacked-size reduction if compression is adopted.
- Moderate package entry-count trade-off if partitioning is adopted.
- Low source reduction.

Main risks:

- Compression may save unpacked bytes but add runtime complexity.
- Per-runtime transformed payloads can reintroduce duplicate content if not
  measured.
- Debuggability can regress if errors point only to offsets.

Validation gates:

- content-provider tests for every runtime.
- registry parity tests.
- packed-package MCP startup.
- package budget tests with byte accounting.
- error-message tests that preserve resource identifiers.

Recommendation:

Compression is complete. Partitioning remains available only if future pack
reports show content-family loading would beat the current single gzip payload.

## Suggested Implementation Plan

The safest high-leverage sequence is:

1. **Artifact Policy Contract** - create a single declarative artifact policy and
   generate/validate package and release surfaces from it.
2. **Source-Only Dist Experiment** - prototype removing committed `dist/src`
   from the development branch while preserving package/release output.
3. **Session Lifecycle Normalization** - move session, document, design gate,
   checkpoints, transition, archive, and ledger effects behind services and
   decorators.
4. **Runtime Descriptor Unification** - merge runtime config, metadata, docs,
   hooks, and invariants into one descriptor model.
5. **Policy Parser Split** - isolate parser/evaluator/provider/hook adapter
   before any parser dependency is adopted.
6. **Test Contract Generation** - replace repeated schema/package/runtime
   assertions with generated contract tests and focused negative tests.
7. **Payload And Docs Pruning** - compress or partition runtime content and
   trim shipped docs with package-budget evidence.
8. **Breaking Decisions** - decide separately on MCP action consolidation,
   runtime portfolio externalization, structured state, and SDK replacement.
